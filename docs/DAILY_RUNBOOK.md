# Complete English — Daily Publishing Runbook (v2)

Read COURSE_SPEC.md and course.config.json before creating any lesson. This runbook describes the scheduled execution and source-of-truth workflow.

## Repository structure

Repository: alextgtome/complete-english; publishing branch: develop.
- docs/COURSE_SPEC.md — canonical pedagogical and UI requirements.
- docs/DAILY_RUNBOOK.md — daily publishing procedure.
- course.config.json — machine-readable duration, start date, timing and historical exceptions.
- data/lesson-manifest.json — **tiny existence manifest** (~324 bytes for 17 days), mapping Day N to its real `everyday`, `workplace` or `interview` classification. READ THIS FIRST for an existence check. Generated by scripts/build-lesson-catalog.mjs.
- data/lesson-records/<type>/day-NNN.json — **individual derived snapshots** of historical and future lesson metadata, including the focus drill; can be fetched without loading the full canonical registry. These JSON files are NOT independently editable; they must match data/lessons.js.
- data/generation-index.json — **compact planning index** with all chunk IDs, first-use days, topics and seven recent lesson contexts. Read ONLY if a new day must be generated. Generated by scripts/build-generation-index.mjs.
- data/lessons.js — full canonical JavaScript registry (window.CE_DATA). Read this only when editing/publishing a day or auditing discrepancies, not automatically at the beginning of every planning run.
- lessons/day-NNN.html — thin page for one day's lesson, referencing shared assets.
- assets/app.js and assets/site.css — shared rendering and interactivity.
- scripts/validate-lessons.mjs — automated checks.
- .github/workflows/pages.yml — validation **before** Pages deployment.

The root index is generated from data/lessons.js; do not add a redundant hardcoded list of days. The browser's localStorage is NOT synchronized with GitHub.

## Daily run (in order)

1. Compute Day N using the current **America/Sao_Paulo calendar date** and 2026-10-29. Do not publish outside days 1–150.
2. **FAST EXISTENCE CHECK FIRST:** calculate Day N; fetch the tiny `data/lesson-manifest.json` (or directly check `lessons/day-NNN.html`, which is already a separate small HTML entry). If Day N is present, fetch ONLY `data/lesson-records/<type>/day-NNN.json` and the corresponding HTML path to confirm the existing lesson, then deliver it. Do NOT read the big cumulative registry, planning index or pedagogical documents for a routine duplicate-day check. If present in only one place, investigate inconsistent state.
   If Day N is **absent**, then read COURSE_SPEC.md, this runbook, course.config.json and data/generation-index.json to plan. This compact index contains all prior chunk phrases and their real first-use days plus recent lesson context. Do not load the old HTML archive or full registry during planning.
3. **Idempotency second check:** confirm Day N is absent in both the small manifest and existing HTML path before authoring. The manifest is derived, not authoritative; if it disagrees with an HTML file, stop and resolve the inconsistency instead of creating another lesson. Classify each new day from config's speaking rotation; old days retain classifications based on their **actual scenario**, not the retrospective 3+2+2 schedule.
4. Check FULL chunk history: compare normalized spelling and semantic meaning; select exactly three genuinely new IDs, three spaced reviews with verified first-use days, a novel topic and one foundations skill. Keep the last seven days' themes varied. **From Day 18, follow the 3+2+2 scenario rotation:** modulo seven (0,3,6) = Everyday; (2,5) = Workplace/Engineering; (1,4) = Interview. This applies only to the main 15-minute speaking segment, not to the 10-minute everyday small talk, which stays EVERY DAY. Preserve at least two weekly workplace sessions for hands-on English: deployment and rollback, AWS service choices, API architecture and contracts, messaging, code reviews, standups, integration and trade-offs. Alternate these topics and require genuine technical explanation plus realistic spoken communication. Do not turn all days into technical interviews or dilute technical workplace practice.
5. **Daily figurative-language/ambiguity checkpoint (Day 18+):** include `ambiguity` with sentence, expression, gist_question, plain_english, context_clue, gist_answer. Place its 60–90-second infer-and-continue micro-practice in the existing 5-minute Noticing block, not as new homework. Follow `course.config.json`: introduce literal vs figurative meaning on Day 19; reinforce with new examples on Days 26 and 33; plan **full focused variations every 28 days** (Days 47, 75, 103, 131), retaining Workplace scenarios and daily small talk. Include new practical contexts and avoid reusing old exercises. On all other days continue the 60–90-second contextual-meaning drill. If a focus day already exists, preserve it and reschedule the deeper theme to the next free Workplace day. Do not automatically call an already-introduced expression NEW.
6. Build one complete lesson obeying the 15 + 35 + 30 + 10 timing and both speaking routes. All six chunks include their own PT-BR translation and "Quando usar"; all other user-facing instructions are English. Within the existing small-talk time, add an **unexpected non-technical question** and practise the scaffold **honest answer → simple detail → optional question back**. Include rapid unrelated daily-life reflex questions. If the learner has no plan, accept uncertainty rather than inventing a story. On Everyday days choose varied settings from food, weather, family, weekends, hobbies, errands, travel, invitations and preferences. On Workplace days, require a concrete engineering task and natural interactive follow-up. Record `scenario_type` in the new day metadata and verify it matches the rotation defined in course.config.json.
7. Design exactly THREE cumulative substitution sequences. Each needs one natural base, 4–6 concrete cues and fully grammatical, coherent intermediate results. Change grammatical units together if needed; attach short note to linked changes. Simulate and **proofread every resulting sentence**, including agreement and idiomatic usage. Never "fix" an intentionally wrong intermediate model answer in the following cue.
8. **Only now read data/lessons.js** (the canonical source), append three new G entries and one Day N record with six IDs, date, prompts, `scenario_type` and fields required by shared UI; add focusDrills[N] and preserve history. **Regenerate BOTH** `data/generation-index.json` (all chunk history) **and** `data/lesson-manifest.json` plus the day's `data/lesson-records/<type>/day-NNN.json` snapshot, using `scripts/build-generation-index.mjs` and `scripts/build-lesson-catalog.mjs` or equivalent exact deterministic output. All derived files must match the same registry version. Do not hand-invent historical metadata or commit snapshots with inconsistent content.
9. Add lessons/day-NNN.html using the neighboring thin template and referencing shared data and assets. Ensure the shared frontend can render this record; don't embed a second lesson copy in HTML.
10. Check everything locally if possible: node --check assets/app.js; node scripts/build-generation-index.mjs --check; **node scripts/build-lesson-catalog.mjs --check**; node scripts/validate-lessons.mjs. The Pages workflow requires all four before deploying. Regeneration and registry edits are one logical atomic change. **Never skip a failing check**, and never claim success based on a commit alone.
11. Commit with authorized GitHub operations and verify the resulting file reads. Check Pages deployment status separately; only link the public URL as confirmed if its deployment succeeds. Otherwise link the GitHub file and explain the status.
12. Deliver a useful concise English lesson summary with the date, time blocks, three new and three review chunks (including their PT-BR translations and "Quando usar" cues) and a real link to the published lesson. Do not claim speaking/writing performance without samples.

## Failure policy and maintenance

- Can't read GitHub registry/spec? Do not assume new chunks are unprecedented; do not blindly publish or create duplicate lessons. Explain the obstacle, provide useful unverified learning material in chat if appropriate.
- Validator fails? Correct the SOURCE first. Do not disable the Pages quality gate to publish.
- Rerun on the same day? Return the existing day's content and no duplicate.
- Found a design bug? Fix the shared assets, not 150 separate lesson HTML files.
- Found a content bug? Fix the canonical registry, regenerate the chunk index AND the typed lesson snapshots/manifest, then add regression tests. Never edit derived JSON files alone.
- Keep changes additive and auditable. Do not commit personal responses, notes, recordings, private data, credentials or secrets to this public repository.
- Changes to the pedagogical approach belong in COURSE_SPEC.md, not appended to the ChatGPT automation prompt. Only change the automation prompt to update its short reference or operating boundaries.
